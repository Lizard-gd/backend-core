# 🔒 Руководство по выбору стратегии блокировок в CRM

## 🎯 Цель документа  
Помочь команде разработки принимать правильные решения при защите данных от конкурентного доступа, избегать **lost update** и грамотно обрабатывать конфликты.

---

## 🧠 Pessimistic Locking (пессимистическая блокировка)

### ⚙️ Как это работает
- Строка в БД блокируется **сразу при чтении** (до начала изменения).
- В PostgreSQL генерируется `SELECT ... FOR UPDATE`.
- Другие транзакции **ждут** освобождения блокировки (ставятся в очередь).
- Блокировка снимается только после `COMMIT` или `ROLLBACK`.

### ✅ Когда использовать в CRM
| Ситуация                                | Пример                                               |
|-----------------------------------------|------------------------------------------------------|
| 💰 Критические финансовые операции      | Списание денег, обновление баланса счёта             |
| 🔄 Конверсия Lead → Deal                | Одновременное изменение статуса Lead и создание Deal |
| 🎫 Резервирование ограниченного ресурса | Последний билет, товар со счётчиком                  |
| 🧨 Операции с высокой конкуренцией      | Десятки менеджеров обрабатывают один Lead            |
| 🛡️ Бизнес не допускает retry           | Операция должна быть выполнена с первого раза        |

### 📝 Реализация в проекте
```java
// В LeadRepository
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT l FROM Lead l WHERE l.id = :id")
Optional<Lead> findByIdForUpdate(@Param("id") UUID id);

// В сервисе
@Transactional
public Lead convertLeadToDealWithLock(UUID leadId, String newStatus) {
    Lead lead = leadRepository.findByIdForUpdate(leadId).orElseThrow();
    lead.setStatus(newStatus);
    return leadRepository.save(lead);
}
```

### 🌟 Плюсы
- ✅ Гарантированное отсутствие потерянных обновлений (lost update)
- ✅ Не требуется писать код обработки конфликтов в бизнес-логике
- ✅ Подходит для очень критичных операций

### ⚠️ Минусы
- ❌ Снижает производительность и масштабируемость (очереди ожидания)
- ❌ Возможны **deadlock'и** (взаимные блокировки) при неправильном порядке захвата ресурсов
- ❌ Увеличивает время ответа для пользователей

## 🍃 Optimistic Locking (оптимистическая блокировка)

### ⚙️ Как это работает
- В сущность добавляется поле `@Version`.
- JPA автоматически управляет версией: при каждом обновлении инкрементирует её и добавляет условие `WHERE version = ?`.
- Если версия изменилась другой транзакцией → обновление не происходит, → выбрасывается `ObjectOptimisticLockingFailureException`.
- Приложение должно перехватить исключение и предложить пользователю повторить действие.

### ✅ Когда использовать в CRM (по умолчанию для всех операций)
| Ситуация                             | Пример                                                                  |
|--------------------------------------|-------------------------------------------------------------------------|
| 📝 Редактирование профиля Lead       | Один менеджер меняет телефон, другой — компанию (конфликт маловероятен) |
| 🧾 Изменение описания / комментариев | Некритичные данные, можно повторить                                     |
| 📦 Массовые batch-обновления         | Можно автоматически повторить при конфликте                             |
| 📚 Read-mostly данные                | Справочники, каталоги, настройки                                        |

### 📝 Реализация в проекте
```java
// В Lead.java
@Version
@Column(name = "version", nullable = false)
@Setter(AccessLevel.NONE)  // JPA управляет версией — не создаём setter
private Long version;

// В сервисе — обычный findById, без блокировки
@Transactional
public Lead updateLeadStatusOptimistic(UUID leadId, String newStatus) {
    Lead lead = leadRepository.findById(leadId).orElseThrow();
    lead.setStatus(newStatus);
    return leadRepository.save(lead);
}
```

### 🌟 Плюсы
- ✅ Высокая производительность и масштабируемость (нет ожидания блокировок)
- ✅ Нет риска deadlock'ов
- ✅ Легко добавляется — достаточно одного поля `@Version`

### ⚠️ Минусы
- ❌ Требуется обработка `OptimisticLockException` в коде (пользователь может потерять введённые данные)
- ❌ Не подходит для операций с очень высокой конкуренцией

## 🩺 Обработка OptimisticLockException в REST API

В проекте используется глобальный `@ControllerAdvice` для возврата HTTP 409 Conflict:

```java
@ExceptionHandler(ObjectOptimisticLockingFailureException.class)
public ResponseEntity<String> handleOptimisticLock(ObjectOptimisticLockingFailureException ex) {
    return ResponseEntity
        .status(HttpStatus.CONFLICT)
        .body("Данные были изменены другим пользователем. Пожалуйста, обновите страницу.");
}
```

На фронтенде (JTE) можно показать сообщение, передав `errorMessage` в модель при редиректе.

## 🧩 Как предотвратить deadlock при pessimistic locking

**Главное правило: всегда блокируйте ресурсы в одном и том же порядке.**

```java
/* 
❌ ПЛОХО: разный порядок блокировок
leadRepository.findByIdForUpdate(id1);
leadRepository.findByIdForUpdate(id2);  // может привести к deadlock

✅ ХОРОШО: сортируем ID перед блокировкой
List<UUID> sortedIds = Stream.of(id1, id2)
    .sorted()
    .toList();
for (UUID id : sortedIds) {
    leadRepository.findByIdForUpdate(id);
}
 */
```

## 📊 Сравнительная таблица

| Критерий                   | 🔒 Pessimistic        | 🍃 Optimistic            |
|----------------------------|-----------------------|--------------------------|
| Вероятность конфликтов     | Высокая               | Низкая                   |
| Критичность данных         | Высокая               | Средняя                  |
| Задержка (latency)         | Выше (ожидание)       | Ниже                     |
| Пропускная способность     | Ниже                  | Выше                     |
| Обработка конфликтов       | Автоматическая (wait) | Ручная (catch exception) |
| Риск deadlock              | Есть                  | Нет                      |
| Использование по умолчанию | **НЕТ**               | **ДА** (@Version везде)  |

## 📋 Чек-лист для разработчика

- [ ] Для всех новых сущностей добавлено поле `@Version`
- [ ] Только для критических операций (конверсия, списание) добавлен `@Lock(PESSIMISTIC_WRITE)`
- [ ] Методы с `@Lock` вызываются внутри `@Transactional`
- [ ] `OptimisticLockException` обрабатывается в контроллере или через `@ControllerAdvice`
- [ ] При блокировке нескольких ресурсов ID сортируются для предотвращения deadlock
- [ ] Включено SQL-логирование для отладки (в dev среде)

---

## 📚 Заключение

- ✅ **По умолчанию используйте оптимистическую блокировку** — добавьте `@Version` во все сущности.
- 🔒 **Пессимистическую блокировку применяйте только там, где конфликты реально возможны и критичны**, например, при конверсии Lead → Deal.
- 🛠️ Всегда сортируйте ID при блокировке нескольких ресурсов, чтобы избежать deadlock'ов.
- 📢 Не забывайте обрабатывать `OptimisticLockException` и давать пользователю понятную обратную связь.
